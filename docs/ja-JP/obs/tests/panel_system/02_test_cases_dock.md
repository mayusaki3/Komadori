# Dock UI 単体テストケース定義

## 1. 目的

OBS Dock UI が Control Core のメッセージ仕様に従い、  
正しくボタン表示とクリックイベント送信を行うことを確認する。

あわせて、

- 「外部仕様として必ず維持すべきテスト」
- 「実装依存でカバレッジ向上を目的としたテスト」

を明確に分離し、Dock UI について **カバレッジ 100% を必須としない理由** を文書化する。

---

## 2. 対象

- 対象モジュール: `src/dock/panel.ts`
- 役割:
  - Control Core からの `page.update` メッセージを受信し、DOM に反映する。
  - ボタンクリックを `button.click` メッセージとして Control Core に送信する。
  - WebSocket の接続状態をステータス表示に反映する。

---

## 3. テスト分類

### 3.1 外部仕様テスト（変更禁止）

Dock UI について、以下は「外部仕様」として扱う。

- `page.update` メッセージの基本的な反映ロジック
- ボタンクリック時に送出される `button.click` メッセージ形式
- 未定義セルの扱い（クリック不可・視覚的な無効状態）
- 接続状態表示（CONNECTED / DISCONNECTED - RETRYING / ERROR）

これらのテストは **OBS-PANEL-Dock-TC-001〜004** として定義し、  
仕様変更時以外の削除・改変を禁止する。

### 3.2 実装依存テスト（変更可能）

上記以外の Dock UI テスト（例: 想定外メッセージの無視、再描画時のクリーンアップ、  
内部的な guard 分岐 など）は **実装依存テスト** として扱う。

- テスト ID は `OBS-PANEL-Dock-TC-XXX` 系を想定する。
- これらは `dock-ui.spec.ts` を一次ソースとし、  
  実装変更に伴い自由に差し替えてよい。

---

## 4. 外部仕様テストケース（OBS-PANEL-Dock-TC-001〜004）

### OBS-PANEL-Dock-TC-001: `page.update` → DOM ボタン反映

- 条件:
  - `currentPage = "main"`
  - `buttons` に `(x=0, y=0, label="LIVE")` を含む
- 手順:
  - 疑似 WebSocket から上記 `page.update` を Dock UI に送信する。
- 確認:
  - `#grid` 配下の該当セル `(0,0)` に "LIVE" が表示される。
  - 該当セルが有効ボタン用のクラス（例: `.btn`）を持つ。

---

### OBS-PANEL-Dock-TC-002: 未定義セルは disabled かつクリックしても送信しない

- 条件:
  - 3x5 グリッドのうち一部セルのみ `buttons` に定義。
  - あるセル `(x,y)` は `buttons` に存在しない（未定義）。
- 手順:
  - `page.update` 受信後、未定義セル `(x,y)` をクリックする。
- 確認:
  - 未定義セルは `.btn.disabled` などの「無効」を示すクラスを持つ。
  - WebSocket 送信メッセージは発生しない（`button.click` が送られない）。

---

### OBS-PANEL-Dock-TC-003: クリック送信内容の検証 (`button.click`)

- 条件:
  - `currentPage = "main"`
  - `(0,0)` に有効なボタンが存在する。
- 手順:
  - 対象セル `(0,0)` をクリックする。
- 確認（送信されるメッセージ）:
  - `type = "button.click"`
  - `payload.page = "main"`
  - `payload.x = 0`
  - `payload.y = 0`
  - `payload.source = "dock"`

---

### OBS-PANEL-Dock-TC-004: 接続状態表示

- 条件:
  - WebSocket 接続成功 / 切断 / エラー を順にエミュレートする。
- 手順:
  - `onopen` / `onclose` / `onerror` ハンドラをトリガーする。
- 確認:
  - `#status` 要素の表示が以下に変化すること。
    - 接続成功時: `"CONNECTED"`
    - 再接続待機中: `"DISCONNECTED - RETRYING"`
    - エラー発生時: `"ERROR"`

---

## 5. 実装依存テストの例（任意・カバレッジ向上用）

以下は **実装依存テスト（OBS-PANEL-Dock-TC-XXX）** の例であり、  
実際のテストコードは `dock-ui.spec.ts` を一次ソースとして管理する。

### OBS-PANEL-Dock-TC-001: 2 回目以降の `page.update` での再描画

- 目的: 同一ページに対する再 `page.update` で、既存ボタンが正しく上書きされることを確認する。
- 要点:
  - 1 回目の `page.update` で "LIVE" を表示。
  - 2 回目の `page.update` で同じセルに "READY" を表示。
  - DOM が二重に増えず、ラベルだけが更新されていること。

### OBS-PANEL-Dock-TC-002: 想定外 `type` のメッセージは無視される

- 目的: Dock UI が未知の `message.type` を安全に無視し、例外を投げないことを確認する。
- 要点:
  - `type: "unknown.event"` のメッセージを送信。
  - 例外が発生しない。
  - 既存の DOM / ステータス表示に変化がない。

### OBS-PANEL-Dock-TC-003: 不正フォーマットの `page.update` は無視（またはログのみ）

- 目的: `currentPage` や `buttons` が欠落した `page.update` を安全に処理すること。
- 要点:
  - `currentPage` なし、`buttons` なしのメッセージを送る。
  - 例外を投げず、既存の表示が保持されること。

※ 上記のような実装依存テストは、  
`src/dock/panel.ts` の分岐・ガードをカバーするために随時追加・変更してよい。

---

## 6. カバレッジ方針（Dock UI で 100% を目指さない理由）

Dock UI は HTML/DOM に強く依存する層であり、  
Control Core に比べて **カバレッジ 100% を必須としない** 方針を取る。

理由は以下の通り:

1. **UI 実装変更の影響が大きい**
   - DOM 構造や CSS クラス名の微細な変更でもテストが大量に壊れる。
   - 100% カバレッジを目標にすると、UI リファクタリング時のテスト修正コストが高くなりやすい。

2. **分岐の多くが「防御的なガード」であり、仕様レベルではない**
   - 例: `#grid` や `#status` が DOM に存在しない場合に throw するガード。
   - これらは「あってはならない事態」に対する保険であり、
     仕様書で保証すべき挙動というよりは、実装の安全対策に近い。
   - すべてのガード分岐をテストで網羅しても、ユーザー価値に対するリターンが小さい。

3. **本質的な仕様は Control Core 側で保証されている**
   - ページ遷移や action 種別ごとの動作、エラーコードなどの重要仕様は Control Core でテスト済み。
   - Dock UI は「Control Core 仕様を UI に反映する薄いアダプタ」であり、
     代表的な経路（OBS-PANEL-Dock-TC-001〜004）さえ抑えれば、
     残りは実装依存テストで柔軟に管理できる。

4. **テストのメンテナンス性を優先するため**
   - Dock UI は将来的にデザインやフレームワークの変更が入りやすい。
   - 100% カバレッジを必須にすると、UI 改修のたびに多数のテストが書き直しになり、
     テスト自体が負債化するリスクが高い。
   - そのため「代表ケース + 重要なエラー表示」のみを仕様テストとし、
     残りは実装依存テストとしてカバレッジ向上に利用する方針とする。

以上より、Dock UI については:

- **外部仕様テスト（OBS-PANEL-Dock-TC-001〜004）** を維持することを最優先とし、
- 残りの分岐は **実装依存テスト（OBS-PANEL-Dock-TC-XXX）** で必要に応じてカバーする。
